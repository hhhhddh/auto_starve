# 生存优化记录

当前 Mod 展示版本：**0.1.6**，本地迭代暂不递增版本号。每次优化使用下文连续的迭代编号记录，代码身份继续由源码 SHA-256 与每轮 build 标识校验。三轮死亡驱动优化已完成；70 个实际游戏日与完整四季仍待验收。

本文件面向使用者和后续维护者，随客户端 Mod 一起安装。双 Mod、取证工具和测试控制器的相关优化集中在这里记录。

## 记录规则

每次优化完成后，在本文件追加下一个迭代编号，再交付或申请下一轮实测。优化编号与实测批次的轮数分别记录，离线界面或工具调整同样记入优化历史。记录至少包含：日期、迭代编号、当前固定的 Mod 版本、观察到的问题、证据与根因、实际修改、验证方法与结果、游戏验证状态、仍需关注的边界。没有证据的猜测保留为待核实项。

资源审查是每轮固定工作：检查照明时机、重复制作或建造、食物和燃料消耗、无效移动及重试，结合实际损耗与生存收益判断。保命储备和必要消耗应保留，库存减少先按事实记录。

公开记录仅使用脱敏后的结论和可重现检查；原始账号、凭据、本机路径、会话标识、日志和私人存档由本机取证目录保存。

## 0.1.1：装备照明与完整死亡取证

- **问题与证据**：首夜多次装备火把返回 `action_unavailable:EQUIP`；角色造火后又外出采购，最终轨迹为 `dark_no_light`。完整死亡 JSON 超过原生日志单行 4095 字节的上限，采集器无法解析截断的通知。
- **根因**：背包自用动作使用了键鼠模式可能拒绝的手柄接口；烹饪与夜间照明没有形成持续保障；死亡轨迹直接输出到日志。
- **修改**：改用原版背包动作选择与发送链路；缺少手持照明时优先使用已有火源并中止普通远行；烹饪按收益安排，复用已有火源；完整轨迹先持久保存，再发送短通知。
- **验证**：装备的房主、远程预测及关闭预测路径、照明、烹饪和双端归档通过离线回归。后续游戏轮次确认火把装备与完整取证生效。

## 0.1.2：连续工作输入

- **问题与证据**：砍树等工作每挥动一次就停顿；原动作链把点击立即松开，并将工具第一次掉耐久当作完成。
- **修改**：CHOP、MINE、HAMMER 对同一目标维持原版工作输入，由状态机接续挥动；完成、取消、紧急抢占、工具损坏或超时时释放输入。材料取得仍依实际持有量确认。
- **验证**：原版状态机离线回归覆盖房主、远程预测和关闭预测；取消与抢占检查通过。持续工作的实际画面连贯性仍待后续实测。
- **检查入口**：`.pi/runtime-recovery/check-continuous-work.py`。

## 0.1.3：照明节约、连续移动与资源记录

- **问题与证据**：原版制作火把后会自动装备，安全黄昏可能提前消耗燃料；导航在中间航点结束旧移动、再下发下一段，出现间歇停顿。原轨迹缺少判断资源收益所需的沿途数量和耐久信息。
- **修改**：区分光源库存准备与实际装备，光照安全时优先收灯，临近入夜约 5 秒才提前装备；洞穴、黑暗或环境光未知时保留照明。已确认安全的中间航点连续交接，最终到点停步与危险打断继续保留。轨迹增加库存、同件装备耐久、独立环境光、入夜倒计时和任务信息；死亡分析列出损耗事实及光源浪费疑点。
- **验证**：照明、连续移动、连续工作和取证的离线回归通过。后三轮证据中未检出自然光充足时光源耗损的新增疑点；这不足以证明所有资源行为均已合理。持续移动的实际画面与窗口失焦运行仍待实测。
- **检查入口**：`check-death-iteration.py`、`check-move-continuity.py`。

## 第一次死亡驱动优化：0.1.3 → 0.1.4

- **证据**：存活约 23 分 23 秒，反复前往已采空的草地，数百次“到达”没有带回材料，最终照明耗尽。
- **根因**：多个地标共用“刚到达”观察，来回切换覆盖了已有结论；走到地标也能重置采购预算。
- **修改**：分别记录各地标观察，跳过当前不可采植物；只有实际资源或制作进展延长采购预算，来源耗尽后转向探索。
- **验证**：空地标往返、植株恢复和无物资进展预算的专项回归通过，旧源码可复现故障。0.1.4 已用于第二轮实测，长期采购可靠性继续验证。
- **检查入口**：`check-empty-landmarks.py`。

## 第二次死亡驱动优化：0.1.4 → 0.1.5

- **证据**：存活约 20 分 6 秒，撤离发条战车后恢复采购，再次进入攻击范围并死亡。
- **根因**：撤退结束距离低于原版索敌范围；路线检查遗漏两点之间的危险区域。
- **修改**：按原版索敌距离提前避让；直达、寻路和连续交接均检查整段路线；拉开安全间距后再恢复采购。
- **验证**：六组专项威胁/撤退回归及相关检查通过，旧源码可复现问题。0.1.5 已用于第三轮实测。
- **检查入口**：`check-threat-retreat.py`。

## 第三次死亡驱动优化：0.1.5 → 0.1.6

- **证据**：存活约 18 分 57 秒，在第三天白天被高脚鸟连续攻击，客户端威胁列表一直为空。
- **根因**：原版高脚鸟具有 `tallbird`/`animal` 标签，却没有策略依赖的 `hostile` 标签。
- **修改**：补齐客户端可见高脚鸟识别，避让范围覆盖原版主动索敌、护巢及春季扩大距离，复用整段检查、紧急抢占和持续撤退。
- **验证**：三组威胁回归能在旧版复现故障、在修复后通过；探索到达回执及相关回归通过。17 个 Lua、3 个 Python 文件通过当轮语法检查。
- **游戏验证状态**：0.1.6 尚未开始下一轮实测。三轮批次已结束，故障世界保持暂停与保存。
- **检查入口**：`check-tallbird-awareness.py`。

## 诊断与控制器维护

这些修正服务于测试基础设施，未另计为生存优化轮次。

- 原版选角回调放入客户端 Mod，自动选择威尔逊、请求出生，并在角色、存档和身份握手就绪后自动生存；已由游戏日志确认。
- 先保存完整双端死亡证据，再由诊断客户端发起原版管理员暂停；两个分片均返回同版本、同会话的真实暂停回执后，才记录暂停成功。已实测确认。
- 停机通知携带 PID、版本与时间并去重，旧通知不能中断健康的新控制器。
- 获准重建时保持旧世界暂停，直接调用项目受控分片的原版重建入口，以双分片新会话和客户端新版本启动确认结果。
- Windows JSON 原子替换遇到临时读句柄占用时，针对 WinError 5/32/33 最长重试 2 秒；持续或其他错误仍失败并保留完整旧状态。文件占用回归通过，同一存档的第三轮已成功恢复。

## 2026-11-12：到达判定与碰撞体积核查

- **关注点**：反复“到达”可能涉及实体碰撞半径、无法进入的目标中心、到达距离或探索目标推进。
- **源码依据**：原版 `LocoMotor:GoToEntity` 在默认接近实体时计入双方物理半径；坐标型 `GoToPoint` 使用显式 `arrivedist`。本 Mod 的导航通过 `WALKTO` 传入该距离，`Navigation.Step` 与 `Actions.check_move` 根据实际位置是否进入同一距离范围判定到达。
- **已有证据**：第三轮有大量探索到达回执落在约 1.4～1.5 米，与探索目标的 1.5 米范围相符；归档未保存足够的目标周边碰撞信息，不能据此排除局部物理卡位，也不能确认碰撞就是反复回执的根因。
- **验证**：离线执行原版目标对象、行走和到达方法，核对实体半径与坐标距离的不同契约；将角色位置固定在目标范围外，验证会重试并有界失败，不会报告成功。检查覆盖房主、远程预测和关闭预测；这是位置模拟，未运行引擎碰撞。探索到达回执仍可清除当前目标并继续选择。
- **本次处理**：保留现有运行逻辑，增加上述契约检查与记录。后续获准实测时，结合目标坐标、实际位置、目标/角色碰撞半径和停滞原因，复核大体积障碍物贴边、洞口、目标选择及远程位置误差；不凭“到达”次数单独认定优化完成。
- **检查入口**：`check-move-continuity.py`、`check-tallbird-awareness.py`。

## 第四次优化（2026-11-12）：顶部进度框与原版重置约定

- **当前版本**：客户端 `0.1.6`、诊断 Mod `0.1.0`，均保持不变；本条是优化记录第 4 次，实测批次仍为已结束的三轮。
- **需求与依据**：普通本地 Lua 修改后沿用可见客户端，使用原版世界重置加载新代码；将左侧进度面板移至窗口上方中间，面板上边界与窗口上边界对齐。
- **原版重置**：本机 Klei 整集群接口为 `c_regenerateworld()`，进入 `TheNet:SendWorldResetRequestToServer()` → `WorldResetFromSim` → `StartNextInstance`/`SimReset` → `TheSim:Reset()` 链路。原版加载入口执行 `ModManager:LoadMods()` 和 `modmain.lua`，客户端通过原版加载流程进入新世界。该过程保留客户端操作系统进程，不使用单分片 `c_regenerateshard()` 替代整集群重置。
- **迭代流程**：现有控制器在证据完整、修复安装并检查通过、获得继续授权后调用整集群重置，保留同一客户端和分片进程。仍要求两个新分片会话与新源码 build 的客户端 `start` 回执，Mod 展示版本相同也可区分旧代码；加载不符合预期时显式阻塞。
- **界面修改**：进度面板采用水平居中、垂直顶部锚点，156 单位高的背景中心向下偏移 78 单位，使背景上沿贴齐窗口顶部。文本和按钮布局保持在面板内。
- **检查**：23 个 Lua、15 个 Python、4 个 JSON 文件通过语法检查；原项目与交接副本的原版重置回放均通过，两轮仅创建同一个客户端进程，新会话及新 build 确认后继续；固定 Mod 版本下的源码更新、首次和再次部署及优化记录同步回归通过。
- **游戏验证状态**：当前仅离线检查，故障世界继续暂停保存；顶部布局及同一客户端进程跨新代码重置的完整实测，待下一次获准运行时确认。

回归文件均在仓库 `.pi/runtime-recovery` 下，通过 `python deploy.py test` 使用维护者本机的原版脚本执行。优化记录保存版本历史；当前本地修改以迭代编号追踪。
